# 기대결과 기반 문장형 TC 실행

## 범위

### 검증 목표와 우선순위

- 테스트 절차는 수행할 동작, 기대결과는 Pass/Fail 판정의 기준이다.
- 사전조건은 실행 준비에 사용한다. 제목과 목적은 참고 정보로 보존한다.
- 제목이나 목적이 절차·기대결과와 다른 맥락이어도 그 차이만으로 Block/Fail 처리하지 않는다.
- 참고 정보에서 별도의 필수 동작, 데이터, 계산·시각 검증 조건을 추가하지 않는다.
- 실제 절차 누락, 기대결과 불충족, 명시된 필수 자료 부재와 위험 동작 제한은 유지한다.
- 기존 결과는 소급 변경하지 않으며 변경된 기준은 새 계획과 실행에 적용한다.

AI 초안에서 내보낸 TestCase Excel 및 `narrative_qa`로 인식된 사람용 TC에
적용한다. `사전조건`, `테스트절차`, `기대결과`를 원문 그대로 보존한다.
`검증결과` 열이 없어도 계획 준비와 실행이 가능하며, 기대결과는 판정 기준이지
Pass/Fail을 쓰는 칸이 아니다. 표준 양식의 `결과`는 과거 수동 결과로 보존하고,
실행한 TC의 `자동화 결과`에 PASS/FAIL/BLOCK/STOPPED/NOT RUN을 기록한다.
과거 결과가 PASS여도 이번 실행은 기대결과를 다시 검사한다.
원본 파일은 덮어쓰지 않고 `실행결과 Excel` 사본을 내려받는다.
표준 업로드는 다른 시트와 미선택 행을 보존하고, 원본을 보존해 기록할 수 없는
이전 형식은 선택 TC를 14열 표준 양식으로 내보낸다.
별도 `실행 상세` 시트에 원본 위치, 절차별 판정, 실제 결과/사유, 캡처 경로를 담는다.

Automation/Recorder와 기존 제한된 수동 검토 실행기의 동작은 변경하지 않는다.
닫혀 있던 레거시 `/api/run` 경로를 다시 활성화하지 않는다.

## 사용 흐름

AI TC RUN은 텍스트가 없어도 UI XML에 클릭 가능하고 활성화된 요소의 실제 bounds가
있으면 `ui-icon` 후보로 수집한다. AI는 캡처의 해당 영역을 확인하여 후보 ID만 선택한다.
클릭 불가능·비활성·잘못된 영역·위험 리소스 ID는 제외하고, 입력 직전에 후보를 다시 확인한다.
아이콘의 의미를 확인할 수 없으면 추측해서 입력하지 않는다. 후보 선택과 ADB 입력 성공은
기대결과 통과와 별개이며, 원문 기대결과 검증까지 완료되어야 자동화 결과를 Pass로 기록한다.

분해된 이동 단계는 해당 단계의 목적지 화면까지만 이동한다. 진입 메뉴가 보이는 것만으로
도착으로 판정하지 않으며, 뒤의 클릭 절차를 먼저 수행하지 않는다. 시각 관찰 중 화면 변화는
입력 없이 한 번 재관찰하고, 계속 불안정하면 Block으로 남긴다. WebView 문서의 비대화형
본문·표에 포함된 저장/삭제 설명은 뒤로가기 확인창으로 취급하지 않는다. 실제 위험 버튼과
확인 문구에 대한 뒤로가기 차단은 유지한다.

1. Excel을 업로드하고 목록에서 TC를 선택한다. 현재 한 번에 1~20개를 지원한다.
2. Run Test Case는 명확한 문구 검증과 제한된 절차만 규칙으로 준비한다.
   AI TC RUN은 선택 TC와 실행 중 화면의 AI 분석 동의를 받은 뒤 원문 절차를
   10개 TC 단위로 해석한다. 준비 중에는 기기를 조작하지 않는다.
3. 버튼 아래에서 TC별 목적, 뎁스, 유형, 사전조건, 원문 절차, 기대결과,
   준비된 동작과 Block 사유를 검토한다. 뎁스는 화면/기능 계층이며 실행 순서가 아니다.
4. `계획 확인 후 실행`을 누른다. 업로드 버전과 계획 해시가 일치해야 실행된다.
5. 사전조건 확인, 절차별 입력, 기대결과 전체 판정을 진행한다.
   화면과 Test Progress, 대시보드에 결과를 남긴다.
6. 완료 후 `실행결과 Excel`을 내려받는다. 기대결과와 실행결과/실제 사유는 별도 열이다.

## 판정과 안전 범위

- AI 실행은 현재 설정된 provider를 사용한다. Codex 실패 시 유료 API로 자동 전환하지 않는다.
- 사전조건 불충족, 비교 자료 부재, 여러 OS/기기 검증, 음성·시간 측정 등은 Block이다.
- 현재 화면 후보로 확인한 탭/스크롤, 명시된 Back/대기, 읽기 전용 관찰만 실행한다.
  임의 좌표, 계정·데이터·시스템 설정 변경이나 결제는 허용하지 않는다.
- 기기 입력 직전에 후보를 다시 확인한다. 화면이 바뀌었거나 대상이 모호하면 입력하지 않는다.
- 최종 기대결과의 모든 조건이 확인돼야 Pass이다. 명확한 불일치는 Fail,
  확인 수단이 없거나 일부만 확인되면 Block이다. AI의 완료 응답만으로 통과시키지 않는다.
- 사전조건 미충족을 AI가 임의 데이터 생성으로 해결하지 않는다. 준비 화면은 운영자가 맞춘다.
- AI 계획 실패 시 명확한 일반 문구 검사만 대체 실행하며 나머지는 Block이다.
- 개별 Fail/Block 이후 다음 TC를 진행한다. Stop 또는 입력 결과가 불확실한 기기 오류는
  남은 TC를 실행하지 않는다. 캡처, 절차, 판정 근거와 실제 AI 사용 지표를 결과 이력에 보존한다.
- 현재 기기의 정지 화면에서 보이지 않는 중간 상태나 장시간 이력을 완전 검증했다고 주장하지 않는다.

## API

- `POST /api/tc-workflow/prepare`: upload_id, file_hash, indices, ai_mode, consent
- `GET /api/tc-workflow/current`: 준비/승인 대기/실행/완료 상태와 원문 계획
- `POST /api/tc-workflow/<id>/start`: plan_digest, approved=true
- `POST /api/tc-workflow/<id>/stop`: 빈 JSON 객체
- `GET /api/tc-workflow/<id>/export`: 완료된 별도 결과 Excel

모든 API는 기존 사내망·Host·Origin·페이지 확인 토큰 검사를 그대로 적용한다.
기존 자동 실행 잠금을 공유하고 실행 중 수동 입력을 차단한다.
계획은 메모리에만 있으므로 서버 재시작 후에는 다시 준비·승인해야 한다.

## 회차별 Fail Review

- Fail Review는 현재 서버 세션의 최신 TC 실행 회차만 표시한다. 서버 재시작 시
  검토 목록은 0건이며, 이전 JSON 기록에서 대기열을 자동 복원하지 않는다.
- 일반/AI TC의 계획 준비나 Excel 업로드만으로는 초기화하지 않는다. 승인된 실행의
  기기 사전 확인을 통과한 후 새 회차를 시작한다. 실패/Stop/스레드 시작 오류가
  그 전에 발생하면 이전 목록을 유지한다.
- 미처리 항목이 있으면 시작 API가 409 `fail_review_reset_required`와 `review`
  (pending, total, token)을 반환한다. 확인 UI는 같은 요청에
  `review_reset_confirmed:true`, `review_reset_token`을 추가해 재전송한다.
  확인 후 다른 브라우저가 검토 내용을 바꿨다면 실행하지 않고 재확인을 요구한다.
- 새 회차에서는 미등록/등록 완료 항목 모두 숨긴다. Redmine 발행·연결 요청과
  초기화를 동시에 허용하지 않으며, 지난 회차 항목의 검토/발행 변경도 거부한다.
- 실제 Fail만 검토 항목으로 추가한다. Block은 앱 결함으로 자동 등록하지 않는다.
  실패 시점 캡처, 원문 절차, 기대결과, 실제 판정 사유를 연결한다. 검토 저장 실패가
  TC 판정을 바꾸지는 않으며 결과에 별도 오류를 남긴다.
- `redmine_failures.json`은 이슈·증거의 결과 조회용 기록으로 보존한다. 캡처 파일이나
  Redmine 서버 이슈를 삭제하지 않는다. `/api/execution/results`는 회차/항목에
  해당하는 `redmine_reviews`를 붙여 결과 페이지에서 등록 이슈 링크를 보여준다.
- 기존 검토 매핑 자동 실행도 같은 초기화 확인을 사용한다. Random/Recorder와
  수동 관찰 실행의 판정 정책은 변경하지 않는다.

## 개발 검증

### 계획 오류 격리와 제한 재계획

- 계획 전용 호출만 응답 전체의 일괄 스키마 검사를 미루고, 각 TC에 스키마/원문 의미 검사를
  적용한다. 실행/시각 검증 호출은 기존 즉시 스키마 검사를 유지한다.
- 정상 계획은 보존한다. 오류 TC는 안전한 오류 코드/필드/안내와 원문으로 한 번만 재계획한다.
  JSON/응답 외곽 구조가 손상되면 묶음을 한 번 재요청하며 이때 개별 TC 추가 재시도는 없다.
- 인증/한도/네트워크/시간 초과는 재시도하지 않는다. 다른 묶음에서도 같은 실패를 반복 호출하지 않는다.
  실패 TC만 일반 실행 가능 여부를 판단하며 유료 API로 자동 전환하지 않는다.
- 조회의 cases[].planning에는 status/retry_count/errors가 포함되고, 오류에는 TC ID, 안전한 코드,
  스키마 필드와 안내만 저장한다. 실행 결과에도 planning을 보존한다. CLI 원본 로그는 저장하지 않는다.
- executable_count=0이면 승인 실행 버튼을 막고 start API도 409로 거부한다. 검토 대기열/기기는 변경하지 않는다.
- 실행은 AI 분석/사전조건 준비/동작 준비/실제 조작/기대결과 검증/완료 상태를 구분한다.
  inputs/input_count는 ADB 성공 응답만 세며, 실제 기대결과 성공은 별도 검증한다.

### 원문 기반 AI 보완과 단계별 판정

- AI 계획은 사전조건, 원본 절차와 기대결과만을 실행 근거로 사용한다. 제목/분류/과거 결과로
  이전 화면이나 연동 데이터를 새로 요구하지 않는다. 위험 동작과 명시적 외부 비교는 제외하지 않는다.
- 계획의 actions에는 원문 source와 basis(procedure/expected), checks에는 expectation 번호와
  after_action 위치가 있다. 모든 원본 절차와 모든 기대결과가 포함되어야 승인할 수 있다.
- navigate는 원문의 목적 화면을 현재 후보에서 찾는다. 사전조건 준비, 기존 임의 항목 선택과
  기대결과에 명시된 복귀 보완을 합쳐 TC당 최대 5개 입력이다. 같은 화면의 효과 없는 조작을
  반복하지 않고, 입력 직전 후보를 다시 검증한다. 실제 불일치는 복구로 숨기지 않는다.
- 본문 확인은 복귀 전에, 복귀 결과는 복귀 후에 검증한다. 최종 Pass는 모든 단계의 실행 근거와
  모든 기대결과의 성공 증거가 있을 때만 가능하다. 일반 Run의 결정적 실행은 유지한다.
- Block 결과에 원문과 부족한 증거를 저장한다. 원본 Excel과 과거 결과는 수정하지 않는다.
- 배포 시 이전 승인 대기 계획은 폐기하고 새 계획을 다시 준비/승인한다. 자동 재실행하지 않는다.

`python -B tests/run_isolated.py`는 실제 기기, 프로세스 실행, 외부 네트워크를 차단한
회귀 검사다. `tools/check_tc_workflow_ui.cjs`는 합성 TC 응답으로 브라우저의 선택,
동의, 승인, 새로고침 복구, 실행 표시와 좁은 화면 배치를 검사한다.
이 테스트는 실제 AI 판단 정확도나 등록된 TC의 기기 실행 성공을 증명하지 않는다.
